# dsh-oc 性能测试结果（2026-08-15）

运行：`node scripts/perf.mjs --sessions N --quiet`（临时 DSH_HOME + mock LLM +
真实 dsh profile + fake opencode 子进程；N=200/1000/5000）。

| 指标 | 200 | 1000 | 5000 | 10000 |
|---|---|---|---|---|
| `GET /session` 热 p50 | ~91ms（未缓存） | ~376ms（未缓存） | ~20ms | ~32ms |
| `GET /api/session` 热 p50 | ~91ms（未缓存） | ~313ms（未缓存） | ~2ms | ~2.5ms |
| `GET /session/:id/message` 冷读 p95 | ~62–87ms | ~302ms | ~1420ms | ~2801ms |
| `GET /api/session/:id/message` 同会话二次读 p95 | — | — | ~1.4ms | ~1.7ms |
| SSE 首事件 | ~0.1ms | ~0.1ms | ~0.16ms | ~0.21ms |
| bridge 启动 | — | ~1204ms | ~2805ms | ~4807ms |
| dsh RSS | ~277MB | ~302MB | ~319MB | ~360MB |

结论与已修复问题：

- **SSE 阻塞（已修复）**：旧实现每收到 `session/title`/`session/created` 事件都会
  `await session.list`，在大量会话下会把 SSE 流卡住数百毫秒到数秒。现改为 250ms
  防抖的后台刷新（`router.ts` `scheduleListRefresh`），mux 流不再等待列表查询；
  回归测试 `tests/bridge-events.spec.ts` 覆盖“title 后 status 不被慢 list 阻塞”。
- **bridge 短 TTL 缓存（新增）**：`session.list` 1s 缓存、`session.history`
  按页 500ms 缓存，任何 mutation 路由与 SSE 事件都会失效。5000 sessions 下
  list 热请求 p50 从 ~1.4s 降到 2–20ms；同一会话二次读 history 约 1ms。
- **>500ms 退化（上游）**：5000 sessions 下 `session.list`/`session.history` 单次
  首次 ~1.3–1.5s，瓶颈在 dsh 存储层的全量会话扫描；bridge 缓存只能消除重复读，
  新会话/冷页的首次读取仍需 dsh 端索引/按 cwd 存储定位优化。
  dsh-oc 侧已避免冗余等待；进一步修复需要 dsh 端索引/按 cwd 存储定位优化。
- 1000 sessions 冒烟（N4 验收规模）全部低于 500ms。
- 10000 sessions：热路径仍为毫秒级；冷读首次 ~2.7–3.0s，随会话数近似线性增长，
  确认瓶颈在 dsh 存储扫描而非 bridge。
