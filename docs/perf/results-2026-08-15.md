# dsh-oc 性能测试结果（2026-08-15）

运行：`node scripts/perf.mjs --sessions N --quiet`（临时 DSH_HOME + mock LLM +
真实 dsh profile + fake opencode 子进程；N=200/1000/5000）。

| 指标 | 200 | 1000 | 5000 | 10000 |
|---|---|---|---|---|
| `GET /session` 热 p50 | ~91ms（未缓存） | ~376ms（未缓存） | ~20ms | ~32ms |
| `GET /api/session` 热 p50 | ~91ms（未缓存） | ~313ms（未缓存） | ~2ms | ~2.5ms |
| `GET /session/:id/message` 冷读 p95 | ~62–87ms | ~302ms | ~1420ms | ~2801ms |
| `GET /api/session/:id/message` 同会话二次读 p95 | — | — | ~1.4ms | ~1.7ms |
| SSE 首事件 | ~0.1ms | ~0.1ms | ~0.16ms | ~0.21ms |
| bridge 启动 | — | ~1204ms | ~2805ms | ~4807ms |
| dsh RSS | ~277MB | ~302MB | ~319MB | ~360MB |

结论与已修复问题：

- **SSE 阻塞（已修复）**：旧实现每收到 `session/title`/`session/created` 事件都会
  `await session.list`，在大量会话下会把 SSE 流卡住数百毫秒到数秒。现改为 250ms
  防抖的后台刷新（`router.ts` `scheduleListRefresh`），mux 流不再等待列表查询；
  回归测试 `tests/bridge-events.spec.ts` 覆盖“title 后 status 不被慢 list 阻塞”。
- **bridge 短 TTL 缓存（新增）**：`session.list` 1s 缓存、`session.history`
  按页 500ms 缓存，任何 mutation 路由与 SSE 事件都会失效。5000 sessions 下
  list 热请求 p50 从 ~1.4s 降到 2–20ms；同一会话二次读 history 约 1ms。
- **启动预取（新增）**：bridge 启动后后台预取 session list，并并行预热最近 5 个
  会话的 tail history；`--session` 续聊还会单独预取目标会话。
- **在途合并与派生页（新增）**：`session.list`/`session.history` 的在途 RPC 由
  并发调用方共享，启动预取与 TUI 首个列表请求不再重复扫描；5000 sessions 下
  `GET /session` 冷读 p95 从 ~1941ms 降到 ~1378ms。full tail 与 100 条消息页
  互相派生缓存，TUI 打开会话时的两次历史读取只产生一次 dsh 扫描。
- **会话列表真实标题（新增）**：dsh `session.list` 不返回 title 投影（实测每行
  都没有 `projections`），真实标题只能从 `session.history` tail 投影读取。
  bridge 在列表请求时补读（≤40 会话全量同步；更大规模不阻塞列表、后台
  低并发补最近 24 个），并缓存到内存，后续列表秒回。

### 2026-08-16 复测（5000 sessions，当前 develop）

| 指标 | 数值 |
|---|---|
| `GET /session` 冷 p95 | ~1.36s（列表扫描为主，标题补读不再阻塞） |
| `GET /api/session` 冷 p95 | ~75ms |
| `GET /session/:id/message` 冷 p50 | ~1.3–1.8s（后台补温低并发下略有争抢） |
| 同会话二次读 | ~2–3ms |
| dsh RSS | ~370MB（含 24 个会话标题投影缓存） |

> 后台标题补温并发为 2、上限 24：既不阻塞列表，也避免与真实历史读取争抢
> 过多资源（此前 8 并发/120 上限会把 5000 会话列表冷读拖到 10s+，已修复）。
>
> 压测报告新增 `measurements.titleCoverage`：`initial`/`afterWarm` 两个快照，
> 量化列表真实标题覆盖率（5000 会话示例：启动预取后 17/5000，后台补温 4s 后
> 23/5000；小规模 ≤40 会话首次列表即全量覆盖）。
- **>500ms 退化（上游）**：5000 sessions 下 `session.list`/`session.history` 单次
  首次 ~1.3–1.5s，瓶颈在 dsh 存储层的全量会话扫描；bridge 缓存只能消除重复读，
  新会话/冷页的首次读取仍需 dsh 端索引/按 cwd 存储定位优化。
  dsh-oc 侧已避免冗余等待；进一步修复需要 dsh 端索引/按 cwd 存储定位优化。
- 1000 sessions 冒烟（N4 验收规模）全部低于 500ms。
- 10000 sessions：热路径仍为毫秒级；冷读首次 ~2.7–3.0s，随会话数近似线性增长，
  确认瓶颈在 dsh 存储扫描而非 bridge。

### 2026-08-16 深夜复测（新增协议路由后，5000 sessions）

新增 health/active/wait/context/single-message/per-session SSE 等端点后复测，
数值与上表一致：`GET /api/session` p50 ≈ 2ms / p95 ≈ 48ms；
`GET /api/session/:id/message` p50 ≈ 1ms / p95 ≈ 2.4ms；
`GET /session` 冷 p95 ≈ 1.36s；`GET /session/:id/message` 冷 p50 ≈ 1.85s；
boot ≈ 2.8s、RSS ≈ 369MB。热路径未受影响，冷读仍为 dsh 上游全量扫描成本。
