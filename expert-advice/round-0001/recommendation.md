# dsh-oc Round 0001 审阅建议

审阅基线：`context.md` 所述 `3c28389`，2026-08-16。本文只基于指定材料及其直接相关的测试/性能/打包文件做静态审阅；按约束未执行安装、构建、测试或 git 写操作。

标记约定：**[事实]** 为代码、脚本、文档或题设直接支持；**[推断]** 为基于这些事实的工程判断；**[需实验]** 为现有证据无法定论的事项。

## 一、结论先行

1. **当前适合受控的 RC/canary 交付，不适合宣称“稳定版”或无条件面向所有用户发布。**
   - **[事实]** 题设报告 mock 全绿且真实模型回归通过；近期关键修复有单测和 e2e，opencode 锁定到 1.18.18，下载资产有 sha256/npm integrity。
   - **[事实]** 真实 LLM 脚本是本地手动项；push CI 只跑 stable 子集，完整 e2e 和规模压测只在手动 workflow 跑。`e2e-tui-abort.sh`、`e2e-tui-continue.sh` 等并不在 push 子集，因此 Thought/中断和恢复标题的真实 TUI 回归不是每次 push 的门槛。
   - **[事实]** 自动化安装的主要路径是“先在 checkout 中 build，再从本地目录安装”；消费者实际使用的 GitHub 源直装路径没有成为发布门槛。`package.json` 没有 `prepare`，exports 指向 `lib/`，所以 GitHub 直装依赖仓库中已提交且匹配源码的构建产物。
   - **[推断]** 这些证据足以说明“主路径能工作”，还不足以说明“发布工件、升级、恢复和随机真实模型事件在用户环境中可重复工作”。建议下一版本命名为新的 RC，而不是 0.1.0 stable。

2. **工具回合 + 排队消息的显示错序，不建议继续无边界地在 bridge 中试错。**
   - **[事实]** bridge 已同时维护稳定消息 ID、父锚点、流式 part、工具状态和 QUEUED 所依赖的未完成态，并把工具回合完成推迟到 `turn/end`。继续调整事件时机可能牺牲“排队立即可见”、工具卡合并或中断收尾中的至少一项。
   - **[事实]** 手测记录称数据完整、无重复，重新进入会话后顺序恢复；同场景官方 opencode 甚至会丢掉工具后的文本。
   - **[推断]** 这强烈指向官方 TUI 的即时渲染/排序状态机，但“官方也有问题”本身并不能证明 bridge 发出的因果顺序正确。
   - **[需实验]** 做下文实验 1：若规范化 SSE/API/history 的顺序、父子关系和 exactly-once 均正确，且最小复现在官方 TUI 上成立，则停止 bridge 修改，向上游提交复现，并在 README 的用户可见“已知限制”中明确记录。该残余可被 RC 接受；在实验完成前不应悄悄归类为已解决。

3. **状态轮询是正确方向；当前“整脚本无条件重试一次”会掩盖一部分真实回归。**
   - **[事实]** `check-all.sh` 的第二次执行覆盖同一个日志文件；重试后通过会让 job 变绿，而失败工件只在最终失败时上传。因此首次失败的证据和 pass-after-retry 频率不会被保留为可审计数据。
   - **[事实]** agent-tab 的轮询接受“窗口内曾看见 label”以及“某一帧 reply count 为 1”，不要求二者在同一最终帧持续成立，也不要求连续稳定帧。
   - **[推断]** 有界轮询比固定 sleep 更可靠，但“曾经成立”不是“最终稳定”。无分类的全脚本重试还会把竞态、性能退化和真实断言失败都当作基础设施噪声。
   - **建议** 仅对明确的启动/连接类基础设施签名做一次重试；语义断言失败不重试。首次失败日志必须保留并在 job summary 计数，即使第二次通过也上传工件。视觉稳定断言至少要求连续 3 帧满足同一谓词，并同时核对 API 终态。

4. **长期最大风险不是“缺一个路由”，而是三个状态机之间的语义漂移。**
   - **[事实]** bridge 实际同时生成 v1 `message.*` 与 v2 `session.next.*` 事件，并依赖官方 TUI 对 `phase`、消息完成态、part ID 和事件先后的具体解释；62/62 probe 主要证明路由存在，不能证明渲染语义。
   - **[事实]** 固定 1.18.18 避免了无预警升级，但也意味着上游修复、安全更新和新协议只能通过一次显式升级进入。
   - **[推断]** 最大维护风险是 dsh 持久事件模型、bridge 的关联/补偿状态、opencode TUI 内部状态机三者任一变化后，端点仍返回 200、probe 仍全绿，但消息顺序、完成态或恢复行为已悄然变化。版本锁定把持续漂移变成周期性的“升级悬崖”，并没有消除漂移。
   - **建议** 把 opencode 二进制当作 vendor ABI：保留当前版本的黄金 HTTP/SSE 轨迹与 TUI 行为基线，为候选新版本建立独立 upgrade lane；升级以语义差分和真实 TUI 回放为门槛，而不是只看 SDK 类型和路由数量。

## 二、最可能遗漏的风险

### P0：发布工件与更新链路尚未被证明

- **[事实]** 用户安装的是可变的 `#main`/`#develop` GitHub ref，包版本仍是 `0.1.0-rc.1`，大量修复位于 `[Unreleased]`。`main` 与 `develop` 当前同步，因而“稳定线/集成线”的行为边界在这个节点不可观察。
- **[事实]** CI 在 checkout 中重新 build，可能把仓库里遗漏或陈旧的 `lib/` 就地修正后再测试；这不能证明 GitHub 下载到的原始 commit 可直接安装。真实 LLM 脚本默认也从 `.` 安装，虽然提供了 `--add-spec`，但它不是自动门槛。
- **[推断]** 同一 package version 配合可变分支会削弱升级确认、缓存失效、问题复现和回滚。用户很难仅从版本号判断自己运行的是哪批 `[Unreleased]` 修复。
- **建议** 下一次交付先形成不可变候选（建议 `v0.1.0-rc.2` tag/明确 commit），让 CLI 显示包版本和 commit；发布门槛应从干净 profile 按 GitHub spec 安装，而不是先 build 本地 checkout。再验证“旧 RC → 候选 RC → 回滚”的完整链路，并检查 `pnpm build` 后 `lib/` 无差异。

### P0：实时、重连、进程重启后的消息身份一致性

- **[事实]** prompt ID、dsh→bridge assistant ID、已广播/已排队 ID 等映射都在 `InteractionState` 内存中；进程重启后不会保留。历史转换的基础 ID 则来自 dsh 持久事件，同一进程内再用这些内存映射做 remap。
- **[推断]** 这不必然导致用户可见重复，因为 TUI 可能在 attach 时完全重取历史；但“实时看到的 ID/父锚点”与“重启后历史返回的 ID/父锚点”是否等价尚未被现有材料证明。队列、插件上下文、工具多 step、打断和 mux 重放组合时风险最高。
- **[需实验]** 必须比较同一会话在 live、SSE 重连、bridge 重启、`--continue`、`--session` 五种视图下的规范化消息图，而不只比较终端文字是否出现。

### P1：真实模型回归的断言强度低于脚本名称暗示

- **[事实]** `e2e-real-llm.sh` 覆盖真实文本、至少一个工具 part、goal、variant 和 TUI attach，是有价值的 smoke。
- **[事实]** 其中 queue probe 最终只断言用户消息数量为 3，没有断言 FIFO 内容顺序、QUEUED 曾出现或工具后文本的位置；TUI 阶段的文本 grep 带 `|| true`，随后只打印 user count，没有断言该次输入完成。goal 走确定性的 slash command，刻意不验证模型是否会主动调用 goal 工具。
- **[推断]** 一次真实模型成功无法覆盖 reasoning 开关、多个并行/串行工具、参数分块、拒绝/错误/中断、无 `[DONE]`、内容块差异和不同 provider 的 stop reason。它应被称为 smoke，而不是完整 release qualification。
- **建议** 用脱敏真实 session JSONL 建立确定性 replay corpus，真实在线模型只负责持续采样新事件形态；不要让随机模型输出承担桥接正确性的唯一 oracle。

### P1：新 history 端点与“大会话”性能仍有空白

- **[事实]** `/api/session/:id/history` 当前先调用未带 `maxMessages/after` 的 `session.history`，转换完整历史，再按 `after` 过滤并按 `limit` 截断。也就是说 `after` 和 `limit` 目前不减少底层读取或转换成本。
- **[事实]** 性能工具默认构造大量、每个仅 3 条消息的会话；它测 v1/v2 message 路由，没有测新增 history 端点和单个超长会话。已有结果也显示存储冷扫随会话数近似线性，5000/10000 会话的首次历史读取约 1.4/2.8 秒。
- **[推断]** 对万级事件的单会话反复增量读取，当前端点可能呈 O(N) CPU/内存和延迟；500ms cache 又会在活跃 SSE 失效后频繁失去收益。响应只返回 `{data, hasMore}`、不回传本页最大 seq，`after` 游标如何由独立客户端推进也需要契约测试澄清。
- **建议** 在声称 v2 history“补齐”前，增加 1k/10k/100k 事件单会话的冷读、连续分页、活跃写入并发基准；若 dsh RPC 暂不支持 `afterSeq`，至少返回明确的 next cursor，并记录当前全量折叠成本。

### P1：标题补温的能力描述与规模行为不完全一致

- **[事实]** 实现对不超过 40 个缺标题的非空会话同步补读；更大列表不阻塞，只后台补最近 24 个、并发 2。性能文档中的 5000 会话样例在 4 秒后只有 23/5000 个真实标题。
- **[事实]** README 把“会话列表真实标题”整体标为 ✅；CHANGELOG 同一段还残留过“同步 12 + 后台 120”的旧描述，而实际常量和性能文档是后台 24。
- **[推断]** 当前策略对性能是合理折中，但产品表述过强：大用户目录初次打开时，大部分项目仍只能显示目录名/id 回退；小于等于 40 个会话时又可能同步承担最多 40 次 tail history RPC。
- **建议** 文档改成“当前页/最近会话渐进补温，目录名/id 回退”，并给同步路径设延迟预算或总时间上限。不要为了提高覆盖率重新扩大后台并发，除非规模基准证明不会复发 10s+ 冷读。

### P1：平台、宿主版本与分支策略

- **[事实]** e2e workflow 只在 Ubuntu x64 跑；资产清单虽覆盖 macOS、Windows、ARM、musl，但信号、PTY、字体/宽度、压缩格式和 resolver 路径没有在该 workflow 的真实平台执行。
- **[事实]** CI 固定安装 `dsh@0.1.0-rc.6`，而部分运行时 peer 采用没有上界的 `>=`。
- **[推断]** opencode 被锁定不代表 dsh 宿主也被锁定；未来 dsh 事件/RPC 变动可能绕过 npm 解析约束进入生产。main/develop 若长期同步且都作为用户安装源，也会增加“修复到底在哪条支持线”的沟通成本。
- **建议** 明确支持矩阵（OS/arch、Node、dsh 版本、opencode 版本），至少加入 Linux x64 + macOS arm64 的发布冒烟；main 只接收通过候选门槛的 commit，develop 保持集成用途，用户文档优先给不可变 tag，分支安装注明为滚动渠道。

## 三、按信息增益排序的下一步实验

### 1. 真实事件差分回放 + 恢复一致性 + 已知错序裁决

- **输入**：已知“工具结果 → 后续文本 + 忙碌中排队”会话；至少 10 个脱敏真实 session（reasoning 有/无、单/多工具、权限拒绝、错误、打断、compaction、插件上下文）；另加一个至少 10k 事件的长会话；固定 opencode 1.18.18。
- **动作**：按 dsh seq 记录原始事件、bridge SSE、v1/v2 message/history 输出；分别在 live、SSE 断开重连、bridge 重启、`--continue` 和 `--session` 后生成规范化消息图，比较 ID 映射、父子关系、part 顺序、完成态和内容哈希。对已知错序同时做官方 opencode 最小复现。长会话记录 history 首屏、连续 `after` 分页的 p50/p95、峰值内存和是否漏页/重页。
- **可证伪断言**：所有视图内容 exactly-once；队列消费顺序与 dsh seq 一致；工具后文本始终归属原回合；重启前后规范化父子图等价；分页无遗漏/重复。性能 SLO 必须在运行前冻结，建议 10k 事件首屏冷读 p95 ≤ 1s、连续热页 p95 ≤ 200ms、bridge 额外 RSS ≤ 100 MiB。
- **停止条件**：出现一次可重复的内容丢失、重复、错误父锚点或分页断裂，就停止“稳定发布”并按首个分叉点归责 bridge/dsh。若连续 20 次规范化轨迹都正确，且视觉错序只在官方 TUI 即时视图复现、重进后恢复，则停止 bridge 试错，文档化并提交上游；不要继续为像素顺序破坏协议不变量。

### 2. 不可变候选的干净安装、升级和回滚演练

- **输入**：前一 RC、候选 tag/commit、`#main`、`#develop`；全新 DSH_HOME；最低和当前支持的 dsh；Linux x64 与 macOS arm64（若继续声称 Windows 可用，再加 Windows x64）。
- **动作**：从 GitHub spec 冷安装候选，不使用本地 checkout 或预先 build；启动并完成一轮文本+工具；退出后从前一 RC 升级到候选、恢复旧会话，再回滚。核对包版本/commit、`src` 对应的 `lib`、锁定二进制版本、冷下载校验、离线复用和 PATH 中的 `dsh-oc`。
- **可证伪断言**：相同不可变 spec 得到相同版本/构建产物；升级后可明确识别新版本且旧会话一致；回滚可操作；每个支持平台都不依赖开发工具链或本地仓库；GitHub 安装不会命中旧 `lib`/旧 package version。
- **停止条件**：任何 stale `lib`、版本仍显示 rc.1、分支缓存导致未更新、恢复不一致、二进制解析失败或宿主版本不兼容，都阻断稳定版；修复后从全新 profile 重跑，而不是在污染环境中续测。

### 3. flake 的统计审计，而不是继续扩大重试窗口

- **输入**：固定 commit、固定 runner 镜像和 1.18.18；permission、agent-tab 及历史上发生过 flake 的脚本；保留每次首次执行的完整产物。
- **动作**：每项至少重复 50 次，关闭“失败即无条件整脚本重试”；按启动/网络/终端捕获/语义断言/性能超时分类。视觉终态改为“同一 API 状态下连续 3 帧相同”，记录首次通过时间分布。之后只给已证明的基础设施签名加定向重试，并始终保存 attempt 1。
- **可证伪断言**：语义失败率为 0；首次执行通过率至少 98%；没有同一失败签名重复两次；稳定时间 p99 低于当前 deadline 的一半。重试不能改变语义结论，只能确认基础设施恢复。
- **停止条件**：同一语义签名出现 2 次，或 deadline/settle 时间持续右移，即认定真实竞态/性能回归并开 bug；不得通过再加一次 retry 或再扩大等待窗口关闭问题。

## 四、方向性建议与发布门槛

**明确建议：未来 1–2 个迭代做功能冻结，以稳定性为主、发布流程为辅、文档为必要收尾；暂不扩功能面。** 可按约 60% 稳定性/一致性、30% 安装发布与 CI、10% 用户文档投入。SDK v2 可实现缺口已基本收口，继续补外围 stub 的信息收益远低于证明现有核心路径可信。

近期可做：

1. 先执行实验 1；它同时决定已知错序是否归上游、恢复是否可靠、history 是否能承受大会话。
2. 通过实验 2 形成 `rc.2` 不可变候选；不要继续用版本号不变的 mutable main 充当发布物。
3. 用实验 3 把 retry 从“消音器”改成有统计、有分类、有首败证据的恢复机制。
4. 发布 RC 前同步 README/CHANGELOG：列出工具+排队即时错序、标题渐进补温、GitHub 滚动分支与 tag 的差别，并修正 120/24 的陈旧描述。

从 RC 升为稳定版的最低退出条件：

- live/reconnect/restart/history 的规范化消息图无丢失、重复和错锚；
- GitHub 不可变 spec 的冷安装、升级、恢复、回滚通过，且源码与 `lib` 一致；
- flake 首败可审计，语义失败不靠 retry 变绿；
- 新 history 端点有单个大会话的性能与分页正确性基线；
- 用户可见文档准确描述上游 TUI 限制、规模退化与支持矩阵。

在这些条件完成前，可以明确标注“RC/canary、锁定 1.18.18、已知显示限制”向愿意反馈的用户交付；不建议把“mock 全绿 + 一次真实模型通过”等同于稳定发布资格。
